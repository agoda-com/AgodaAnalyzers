# Do Not Use Hardcoded Delays in Test Code

ID: AG0052

Type: Test Quality

## Summary

Detect `Task.Delay` and `Thread.Sleep` calls with hardcoded durations in test code. These are timing-dependent waits that make tests flakey — they either wait too long (slowing CI) or not long enough (causing intermittent failures on slower machines).

## Explanation

`Task.Delay` and `Thread.Sleep` with hardcoded values in test code is problematic because:
- CI machines have variable load and may be slower than developer machines
- The required delay depends on system state, not a fixed duration
- They add unnecessary wait time to test suites
- They mask the real issue: lack of proper synchronization or event-driven waiting

This rule complements AG0023 which prevents `Thread.Sleep` globally. This rule targets both `Task.Delay` and `Thread.Sleep` with hardcoded durations specifically in test code.

### Don't ❌

```csharp
// BAD: Hardcoded delay to wait for async operation
[Test]
public async Task Should_update_status_after_processing()
{
    await _service.StartProcessingAsync(orderId);
    await Task.Delay(2000); // hope 2 seconds is enough...
    var status = await _repository.GetStatusAsync(orderId);
    Assert.That(status, Is.EqualTo(OrderStatus.Completed));
}

// BAD: Delay in a polling loop with hardcoded interval
[Test]
public async Task Should_eventually_publish_event()
{
    await _publisher.PublishAsync(new OrderCreatedEvent(orderId));
    for (int i = 0; i < 10; i++)
    {
        await Task.Delay(500); // fixed 500ms intervals
        var events = await _eventStore.GetEventsAsync(orderId);
        if (events.Any()) return;
    }
    Assert.Fail("Event was not published in time");
}

// BAD: Delay with TimeSpan.FromSeconds
[Test]
public async Task Should_wait_for_cache_expiry()
{
    await Task.Delay(TimeSpan.FromSeconds(5));
}

// BAD: Delay in test setup
[SetUp]
public async Task Setup()
{
    await _container.StartAsync();
    await Task.Delay(5000); // wait for container to be ready
}
```

### Do ✅

```csharp
// GOOD: Use explicit waits for async state changes
[Test]
public async Task Should_update_status_after_processing()
{
    await _service.StartProcessingAsync(orderId);
    var status = await WaitForConditionAsync(
        () => _repository.GetStatusAsync(orderId),
        s => s == OrderStatus.Completed,
        timeout: TimeSpan.FromSeconds(10));
    Assert.That(status, Is.EqualTo(OrderStatus.Completed));
}

// GOOD: Use health checks for container readiness
[SetUp]
public async Task Setup()
{
    await _container.StartAsync();
    await _container.WaitForHealthyAsync(timeout: TimeSpan.FromSeconds(30));
}

// GOOD: Use event-driven waiting with Task.WhenAny (timeout pattern — not flagged)
[Test]
public async Task Should_eventually_publish_event()
{
    var tcs = new TaskCompletionSource();
    _eventStore.OnEventReceived += (_, _) => tcs.TrySetResult(true);
    await _publisher.PublishAsync(new OrderCreatedEvent(orderId));
    var received = await Task.WhenAny(tcs.Task, Task.Delay(TimeSpan.FromSeconds(10)));
    Assert.That(received, Is.EqualTo(tcs.Task), "Event was not published in time");
}

// GOOD: Configurable delay via test settings (if delay is truly needed)
[Test]
public async Task Should_handle_rate_limiting()
{
    await Task.Delay(TestSettings.RateLimitWindow); // configurable, not hardcoded
    var result = await _client.SendRequestAsync();
    Assert.That(result.StatusCode, Is.EqualTo(200));
}
```

## What This Rule Flags

- `Task.Delay(literal_int)` — e.g. `Task.Delay(1000)`
- `Task.Delay(TimeSpan.FromMilliseconds(literal))` — and `FromSeconds`, `FromMinutes`, etc.
- `Task.Delay(new TimeSpan(literal, literal, literal))`
- `Task.Delay(constant_expression)` — e.g. `Task.Delay(5 * 200)`
- `Thread.Sleep(literal_int)` — e.g. `Thread.Sleep(1000)`
- `Thread.Sleep(TimeSpan.FromSeconds(literal))`

## What This Rule Does NOT Flag

- `Task.Delay` / `Thread.Sleep` with a variable or configurable duration
- `Task.Delay` used inside a `Task.WhenAny` (timeout pattern)
- Delays in non-test code (outside `[TestFixture]`, `[TestClass]`, `[Fact]`/`[Theory]`, `[Test]` contexts)

## Root Cause Data

This rule addresses **Category C1 (Race condition / timing)** from flakey test analysis — the #1 root cause at 47% of all flakey test MRs.
