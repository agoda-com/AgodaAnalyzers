# AG0054: SpecFlow [Binding] partial class is split across multiple files

## Cause

A SpecFlow or Reqnroll `[Binding]` class is declared as `partial` and its declarations span multiple source files.

## Rule description

SpecFlow step definition classes decorated with `[Binding]` should not be split across multiple files using partial classes. When step definitions for a single binding class are scattered across files, the SpecFlow runtime binding resolution can become unreliable, leading to intermittent test failures where steps cannot be found at runtime.

This is especially problematic when:
- Classes share ambient state via `ScenarioContext` or constructor injection
- The binding scanner encounters ordering-dependent conflicts
- Step definitions are moved between files during refactoring

## How to fix violations

Consolidate all partial class declarations into a single file. Move all step definition methods (`[Given]`, `[When]`, `[Then]`) for the binding class into one file and remove the `partial` modifier.

## Bad example

```csharp
// File: OrderSteps.Part1.cs
[Binding]
public partial class OrderSteps
{
    [Given(@"a customer with id '(.*)'")]
    public void GivenACustomerWithId(string customerId) { }

    [When(@"the customer places an order")]
    public void WhenTheCustomerPlacesAnOrder() { }
}

// File: OrderSteps.Part2.cs  <-- SPLIT!
[Binding]
public partial class OrderSteps
{
    [Then(@"the order status should be '(.*)'")]
    public void ThenTheOrderStatusShouldBe(string expectedStatus) { }
}
```

## Good example

```csharp
// File: OrderSteps.cs — all steps in one file
[Binding]
public class OrderSteps
{
    [Given(@"a customer with id '(.*)'")]
    public void GivenACustomerWithId(string customerId) { }

    [When(@"the customer places an order")]
    public void WhenTheCustomerPlacesAnOrder() { }

    [Then(@"the order status should be '(.*)'")]
    public void ThenTheOrderStatusShouldBe(string expectedStatus) { }
}
```
