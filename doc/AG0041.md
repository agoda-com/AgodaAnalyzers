# Use Message Templates in Logging

ID: AG0041

Type: Bug / Performance / Best Practice

## Summary

Use structured logging with message templates instead of string interpolation or concatenation. This improves performance, enables better log analysis, and follows logging best practices.

## Explanation

String interpolation and concatenation in logging:

- Reduces performance due to unnecessary string operations
- Makes log analysis more difficult
- Loses semantic information
- Can't be properly indexed or searched
- Doesn't support structured data
- Creates inconsistent log formats

### Don't ❌

```csharp
// String interpolation - loses structure
logger.Information($"User {userId} logged in at {DateTime.Now}");

// String concatenation - poor performance
logger.Information("Error occurred: " + errorMessage);

// Multiple interpolations
_logger.LogError($"Failed to process order {orderId} for user {userId} with error: {error}");

// Exception-first overload - the template is still interpolated
logger.Error(ex, $"Failed to load rates for {propertyId}");
```

### Do ✅

```csharp
// Message templates with named parameters
logger.Information("User {UserId} logged in at {LoginTime}", userId, DateTime.Now);

// Simple message template
logger.Information("Error occurred: {ErrorMessage}", errorMessage);

// Multiple parameters
_logger.LogError("Failed to process order {OrderId} for user {UserId} with error: {Error}", 
    orderId, userId, error);

// Exception-first overload - the exception stays first, the template becomes a literal
logger.Error(ex, "Failed to load rates for {PropertyId}", propertyId);
```

## What Is Detected

The rule reports the *message template* argument of a logging call.

A call is a logging call when the invoked method is declared on one of:

* `Serilog.ILogger` (or any type implementing it, such as `Serilog.Core.Logger`)
* `Serilog.Log` — the static entry point, e.g. `Log.Information(...)`
* `Serilog.LoggerExtensions`
* `Microsoft.Extensions.Logging.ILogger` (including `ILogger<T>`)
* `Microsoft.Extensions.Logging.LoggerExtensions` — the `LogInformation` / `LogError` / … extension methods

Because it is the *declaring type of the invoked method* that is matched, it does not matter how
the logger is reached: fields, properties, locals, parameters and the static `Log` class are all
covered, while an unrelated type that happens to expose an `Information(...)` member is not.

The template argument is the first argument that is a string literal, an interpolated string or a
string concatenation. Leading `Exception` and `Microsoft.Extensions.Logging.EventId` arguments are
skipped, so the `logger.Error(ex, template, …)` and `logger.LogInformation(eventId, template, …)`
overloads are inspected too. The diagnostic is raised only when that argument is an interpolated
string or a concatenation.

## What The Code Fix Does

The fix rewrites the interpolation or concatenation into a literal message template plus arguments.
Every argument that was not part of the template — the leading exception or `EventId`, and anything
that followed the template — is preserved in place.

Placeholder names are derived from the interpolated expression and sanitised to `[A-Za-z0-9_]+`, so
the result is always a legal structured-logging property name:

| Expression | Placeholder |
| --- | --- |
| `hotelId` | `{HotelId}` |
| `ex.Message` | `{Message}` (last identifier of the member access) |
| `fromDate.ToShortDateString()` | `{FromDate}` (the receiver, since that is what is being logged) |
| `nameof(GetRate)` | `{GetRate}` |
| `age + 1`, `x ? a : b`, casts, … | `{Arg1}`, `{Arg2}`, … |

Names collide often once they are shortened, so duplicates within one template get a numeric
suffix: `$"{a.Id} {b.Id}"` becomes `"{Id} {Id2}"`.

Format specifiers and alignment are carried over (`$"{price:F2}"` → `"{Price:F2}"`,
`$"{x,10}"` → `"{X,10}"`), braces in literal text stay escaped so Serilog does not read them as
empty placeholders, and verbatim (`$@"…"`) and raw (`$"""…"""`) interpolated strings are emitted as
normal, correctly escaped string literals.

The fix is also registered for Sonar's `S2629` (*Don't use string interpolation in logging message
templates*), so repositories that run `SonarAnalyzer.CSharp` get it without enabling AG0041. Fix All
is supported, which means `dotnet format analyzers --diagnostics AG0041` works across a solution.

## Why Use Message Templates?

- Better performance (avoids string operations when not logging)
- Enables structured logging
- Supports semantic logging
- Easier to analyze and search logs
- Maintains consistent log formats
- Works better with modern logging frameworks
- Allows for proper indexing and querying
- Adds valuable metadata to log events

Remember: Message templates should always be literal strings, with parameters passed as separate arguments.
